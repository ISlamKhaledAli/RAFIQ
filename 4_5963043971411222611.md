## Findings

### F-01 - Invoice discount applied twice when it is not larger than existing item discounts
- **Category:** Financial defect. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Process / roles:** POS checkout, cashier.
- **Evidence:**
  - `frontend/src/views/PosView.tsx` 490-533 `handleApplyInvoiceDiscount`: when `totalPiastersToDiscount <= existingItemDiscountsSum`, the whole entered amount is treated as *extra*, distributed into the lines (lines now contain item + invoice discount), but `setDiscountPiasters(totalPiastersToDiscount)` stores only the invoice part.
  - `PosView.tsx` 553: `effectiveDiscountPiasters = max(discountPiasters, sumItemDiscounts)` - the screen shows the correct combined discount.
  - `PosView.tsx` 932: payload sends `discountPiasters` = invoice part only, while `items[].discountPiasters` already include it.
  - `desktop/Services/SaleService.cs` 509-527: when `sale.DiscountPiasters < existingItemDiscountsSum` the server treats `sale.DiscountPiasters` as *another* extra discount and distributes it again.
- **Example:** item discount 30 EGP, then invoice discount 20 EGP. Screen: total discount 50. Saved: 70.
- **Expected:** saved discount = discount shown to cashier and customer.
- **Actual:** saved discount is higher by the invoice discount amount.
- **Consequence:** revenue and profit understated; for anonymous customers the "overpayment" becomes change, for registered customers it is credited to their account as a deposit (real money liability). Receipt reprints show different totals than what was collected.
- **Root cause:** ambiguous contract - `DiscountPiasters` sometimes means "total discount", sometimes "extra invoice discount", and client and server guess differently.
- **Proposed fix:** define one contract: client sends only line `discountPiasters` (already including the distributed invoice share) and `discountPiasters = sum(line discounts)`; server must never redistribute when line discounts are present (keep distribution only when lines carry zero discount). Optionally send a separate `invoiceDiscountPiasters` field for auditing.
- **Regression risk:** existing TEST-9 compatibility branch in `SaleService` relies on the ambiguous behaviour; C# runners must be updated.
- **Tests:** item-only; invoice-only; item then invoice smaller; item then invoice larger; invoice then item; verify `sales.total_piasters` equals screen total in each.
- **Decision needed:** No.

### F-02 - Shift closing and daily closing compute "expected cash" with different, incomplete formulas
- **Category:** Financial / reconciliation defect. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Process / roles:** shift close, daily Z-report; cashier, owner.
- **Evidence:**
  - `desktop/Repositories/ShiftRepository.cs` 294-520 `CalculateShiftMetrics`: expected = opening float + cash sales - cash returns + debt payments - drawer expenses + cash in - cash out. It **omits** e-pay drawer cash, e-pay drawer funding, wallet cash-in/cash-out drawer movements, wallet drawer funding, purchases paid from drawer, supplier payments from drawer. The `shifts` table has columns for these (`epay_cash_piasters`, `wallets_cash_piasters`, `purchases_cash_piasters`, `supplier_payments_cash_piasters`) but they are never computed here.
  - `desktop/Services/DailyClosingService.cs` 567-578: expected includes e-pay, wallets, purchases, supplier payments but **omits** shift opening float and manual cash-in / cash-out (`cash_drawer_transactions`), and clamps negatives to 0.
- **Expected:** one formula, one source of truth, used by both shift close and daily close, covering every movement that physically touches the drawer.
- **Actual:** any store using Fawry/wallet services, paying suppliers from the drawer, or doing cash-in/out will see false shortages or overages in at least one of the two reports.
- **Consequence:** cashiers wrongly blamed, real theft hidden, owner loses trust in Z-report.
- **Proposed fix:** extract a single `DrawerCashCalculator` (time-window + optional shift id) used by both; include all movements; never clamp to 0 (a negative expected value is itself an alarm).
- **Tests:** scenario day with: opening float, cash sale, cash return, debt payment, drawer expense, e-pay cash-in, terminal funding from drawer, wallet cash-out, purchase paid cash, supplier payment, manual cash-in/out -> shift expected == daily expected == hand-calculated value.
- **Decision needed:** D-1.

### F-03 - Cash overpayment by a registered customer is counted as sales revenue in daily closing
- **Category:** Financial / reporting defect. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Evidence:** `DailyClosingService.cs` 141: `total_sales = SUM(CASE WHEN paid-fee > total THEN paid-fee ELSE total END)`. The overpayment becomes a customer deposit (`customer_ledger` type `deposit`, `SaleRepository.cs` ~760), i.e. a liability, not revenue.
- **Consequence:** daily sales inflated; if the customer later uses the deposit, the same money is counted again as sales.
- **Proposed fix:** `total_sales = SUM(total_piasters)`; report deposits separately as "customer advances received".
- **Tests:** registered customer pays 120 for a 100 invoice and leaves 20 on account -> sales 100, advances 20, drawer cash +120.

### F-04 - Wallet / InstaPay balance update failure is silently swallowed inside the sale transaction
- **Category:** Data integrity. **Severity:** P2. **Confidence:** High.
- **Evidence:** `SaleRepository.cs` ~520-580: digital account credit is wrapped in `try { ... } catch { Logger.Warn }`. If no active account of that type exists, nothing is recorded at all (no error).
- **Consequence:** sale committed as InstaPay paid while the wallet balance and `digital_transactions` are not updated; wallet reconciliation drifts; a later cancellation finds no `pos_sale` row and does not reverse.
- **Proposed fix:** remove the catch; if no active account exists, reject the sale with a clear Arabic message (or require selecting the account explicitly in `DigitalPaymentModal`).
- **Tests:** InstaPay sale with no active InstaPay account -> sale rejected; with account -> balance + tx row created.

### F-05 - Client-supplied `isExpiredBypass` allows selling expired stock without supervisor PIN
- **Category:** Security / business rule. **Severity:** P2. **Confidence:** High.
- **Evidence:** `SaleRepository.cs` 227 and 336: `else if (item.IsExpiredBypass) authorized = true;`. The flag comes from JSON (`Models/Sale.cs:66`, `PosView.tsx:380`).
- **Consequence:** any caller of `sales:create` can bypass the expired-product block; audit log records an override without a real supervisor.
- **Proposed fix:** ignore client flag; require `SupervisorPin` verification (or a server-issued override token from `auth:verifySupervisor`).
- **Tests:** expired product with flag and no PIN -> rejected.

### F-06 - Hardcoded supervisor PINs in credit-limit override
- **Category:** Security. **Severity:** P2. **Confidence:** Medium (path only active when `DatabaseService.Security == null`).
- **Evidence:** `SaleRepository.cs` 655: `"1234" || "8963906" || "SUPERVISOR_TEST_PIN"`.
- **Proposed fix:** delete the fallback; fail closed when the security service is unavailable.

### F-07 - Customer debt payments carry no payment method; all treated as drawer cash
- **Category:** Market fit / reconciliation. **Severity:** P2. **Confidence:** High.
- **Evidence:** `CustomerRepository.cs` ~403 inserts `customer_ledger` type `payment` with no method; `DailyClosingService` and `ShiftRepository` add every `payment` to expected cash.
- **Consequence:** in Egypt many customers settle "الشكك" via InstaPay / Vodafone Cash; those payments create false drawer overages and wallet balances are not credited.
- **Proposed fix:** add `payment_method` (+ `digital_account_id`) to debt payments; route non-cash to wallet balance; closing counts only cash.
- **Decision needed:** D-2.

### F-08 - Daily closing gross profit is clamped at zero
- **Category:** Reporting. **Severity:** P2. **Confidence:** High.
- **Evidence:** `DailyClosingService.cs` ~330: `Math.Max(0, GrossProfit - returnedProfit)`; the expected cash is also clamped (~579).
- **Consequence:** loss days (heavy returns, damaged goods, below-cost sales) shown as zero profit; owner misled.
- **Proposed fix:** remove clamps; display negative values in `danger` colour.

### F-09 - Checkout idempotency cache is in memory only
- **Category:** Reliability. **Severity:** P3. **Confidence:** Medium.
- **Evidence:** `SaleService.cs` 28-60: static dictionary, 200 entries, lost on restart.
- **Consequence:** crash after commit but before UI receives the response, then retry after restart (cart draft restored from `localStorage`) -> duplicate invoice and double stock deduction.
- **Proposed fix:** persist `idempotency_key` in `sales` with a UNIQUE index; return existing sale on conflict.

### F-10 - Return without invoice has no approval and no price ceiling when the PIN system is disabled
- **Category:** Security / fraud. **Severity:** P2. **Confidence:** High.
- **Evidence:** `ReturnService.cs` 78-96: PIN check only `if (pinStatus.IsEnabled)`. `ReturnRepository.cs` 134-146: for no-invoice returns, total = client unit price x qty, not compared to catalogue price.
- **Consequence:** any user with `returns.create` can pay cash out of the drawer for arbitrary goods at arbitrary prices.
- **Proposed fix:** require a dedicated permission (`returns.without_invoice`) always; cap unit price at the catalogue price unless `pos.price_override`.

### F-11 - Supervisor-override audit entries from the POS screen are rejected for cashiers
- **Category:** Audit trail. **Severity:** P3. **Confidence:** High.
- **Evidence:** `PosView.tsx` 468 and 525 call `auditLogs:create`, mapped to `REQUIRE_ADMIN` (`IpcDispatcher.cs:414`); errors swallowed with `.catch(() => {})`.
- **Consequence:** the exact case that needs audit (cashier with supervisor approval) is never logged from the UI.
- **Proposed fix:** log overrides server-side inside `sales:create` (already partially done) and remove the client calls.

### F-12 - `templates:apply` bypasses authorization at any time
- **Category:** Security. **Severity:** P2. **Confidence:** Medium. **Status:** Potential issue - verify in C8.
- **Evidence:** `IpcDispatcher.cs` ~545: `if (request.Action == "templates:apply" || (firstRun && settings:save)) return null;` - the first-run condition applies only to `settings:save`.
- **Consequence:** an unauthenticated or cashier session could re-apply a store template (may seed categories/products/settings).
- **Proposed fix:** allow only when `IsFirstRunNeeded()`.

### F-13 - Card refunds have no validation ceiling
- **Category:** Financial. **Severity:** P3. **Confidence:** Medium.
- **Evidence:** `ReturnService.cs` ~370-400 validates `cash`, `instapay`, `wallet` refunds against the original payment; `card` (and any other string) falls through with only the overall-total check.
- **Consequence:** a return on a cash/credit sale can be recorded as "card refund", hiding where money actually went; closing excludes it from drawer, so a cash payout recorded as card makes the drawer short with no trace.
- **Proposed fix:** whitelist refund methods; validate card against card paid.

### F-14 - Refund on a credit sale that the customer later paid off cannot be refunded in cash
- **Category:** Business rule / UX. **Severity:** P3. **Confidence:** Medium.
- **Evidence:** `ReturnService.cs` ~320: for `credit` sales `netCashPaidOnOrig = PaidPiasters` (down payment only); later debt payments are not linked to the invoice.
- **Consequence:** cashier must refund "to account", leaving the customer with a credit balance; customer expects cash; workaround is manual cash-out (untracked reason).
- **Decision needed:** D-3.

### F-15 - Shift-level cash returns and debt payments are selected by time window, not by shift id
- **Category:** Reconciliation. **Severity:** P3. **Confidence:** High.
- **Evidence:** `ShiftRepository.cs` returns and debt queries use `created_at BETWEEN opened_at AND closed_at` (no `shift_id`).
- **Consequence:** if two shifts overlap (e.g., second register, or shift opened before the previous was closed after a crash), the same refund is counted in both shifts.
- **Proposed fix:** store `shift_id` on `returns`, `customer_ledger` payments, `cash_drawer_transactions`, e-pay and wallet transactions; filter by it.

## C6 findings (cash drawer, shifts, e-pay terminals, wallets, expenses)

### F-16 - E-pay fee, provider commission, machine deduction and net profit are trusted from the client
- **Category:** Financial / fraud. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Process / roles:** Fawry / Aman / Masary style service sale; cashier, owner.
- **Evidence:**
  - `desktop/Bridge/IpcDispatcher.Epay.cs` 174-222: payload deserialized directly into `EpayTransaction`; only sign checks.
  - `desktop/Repositories/EpayRepository.cs` ~640-680 `CreateTransaction`: `CustomerFeePiasters`, `ProviderCommissionPiasters`, `MachineDeductedPiasters` taken as sent; `NetProfitPiasters` used as sent when `> 0`; if `MachineDeducted < Bill` the difference is added to profit. `CalculatePricing` (the server-side rule engine) is never called during creation.
- **Expected:** server recomputes fee, commission, machine deduction and profit from the terminal rules; client values are only accepted as an explicit, permission-checked override.
- **Actual:** a cashier (or a modified UI) can record a lower fee than collected (skimming the difference), or inflate / deflate profit and machine balance.
- **Consequence:** commission income under-reported, terminal balance no longer matches the provider's statement, drawer differences unexplained.
- **Proposed fix:** call `CalculatePricing` inside `CreateTransaction`; reject mismatches unless the user has `epay.price_override`; never accept `NetProfitPiasters` or `MachineDeductedPiasters` from the client.
- **Tests:** payload with fee 0 when rule says 5 EGP -> rejected; payload with `netProfitPiasters` 10000 -> ignored; per_thousand and percent min/max caps.

### F-17 - Closed-day protection in e-pay / wallets / fundings ignores the business-day cutoff, and e-pay cancellation has none
- **Category:** Data integrity / reconciliation. **Severity:** P2. **Confidence:** High.
- **Evidence:**
  - `EpayRepository.cs` 381 (funding) and ~700 (transaction), `DigitalAccountRepository.cs` ~617: `WHERE business_date = date('now','localtime')` - calendar date, not `business_day_cutoff_hour` used by sales and daily closing.
  - `EpayRepository.cs` 825-960 `CancelTransaction`: no closed-day check, reason optional, no drawer movement recorded for the cash handed back.
- **Consequence:**
  - Shops working past midnight (cutoff e.g. 4 AM): after midnight the check looks at the next calendar day, so e-pay/wallet cash can be posted into an already sealed business day, or wrongly blocked.
  - Cancelling yesterday's (sealed) e-pay transaction today changes the terminal balance; today's drawer pays the customer back but nothing records that outflow, so today's closing shows a false shortage of the same amount, and yesterday's sealed figures silently no longer match the live data.
- **Proposed fix:** one helper `BusinessDay.IsClosed(conn, trans, utcNow)` used everywhere; cancellation after closing must post a reversing entry on today's business date (contra entry) instead of flipping the original status; reason mandatory.
- **Tests:** cutoff 4 AM, closing sealed at 23:00, e-pay at 01:00 -> rejected; cancel sealed-day e-pay -> creates today's reversal, original untouched.

### F-18 - Wallet / InstaPay transactions cannot be cancelled or reversed
- **Category:** Missing workflow. **Severity:** P2. **Confidence:** High.
- **Evidence:** no cancel/reverse method in `DigitalAccountRepository.cs`; no `wallets:cancel*` action in `IpcDispatcher.cs` permission map or `IpcDispatcher.Wallets.cs`.
- **Consequence:** a typo (e.g. 5000 instead of 500) can only be "fixed" by a manual funding / balance edit, which does not reverse the drawer cash or the profit; daily closing and wallet analytics stay wrong permanently.
- **Proposed fix:** `wallets:cancelTransaction` mirroring e-pay cancellation (contra entry, reason, permission `wallets.cancel`, closed-day rule from F-17); add to RBAC matrix (AGENTS rule 8).

### F-19 - Wallet "cash_in" pays cash out of the drawer without checking drawer cash
- **Category:** Cash control. **Severity:** P3. **Confidence:** High.
- **Evidence:** `DigitalAccountRepository.cs` 682-690: `cash_in` drawer effect is `profit - amount` (cash leaves the drawer), but unlike e-pay `cash_out` (`EpayRepository.cs` ~710) there is no `GetLiveDrawerBalance` check.
- **Consequence:** the system records a payout the drawer could not physically make; difference surfaces only at closing.
- **Proposed fix:** same drawer sufficiency check as e-pay cash-out (using the unified calculator from F-02).

### F-20 - Terminal / wallet balance can be overwritten from the edit form
- **Category:** Data integrity / audit. **Severity:** P2. **Confidence:** High (e-pay), Medium (wallets, line 255 same pattern).
- **Evidence:** `EpayRepository.cs` 148-225 `SaveTerminal`: `balance_piasters = @balance` from the payload; difference logged as `manual_adjustment` with `created_by='admin'` and audit `UserId="admin"` regardless of the real user. `DigitalAccountRepository.cs` ~255 updates `balance_piasters = @balance` the same way.
- **Consequence:** anyone with `epay.terminals_manage` / `wallets.accounts_manage` can change money balances without a reason, outside the funding workflow, with a false audit identity.
- **Proposed fix:** make balance read-only in save; balance changes only via funding / adjustment command with reason, real user id, and its own permission.

### F-21 - Fee calculations use floating point
- **Category:** Financial precision (violates AGENTS rule 1). **Severity:** P3. **Confidence:** High.
- **Evidence:** `SaleService.CalculateEpayServiceFee` (`double pct`, `Math.Round(total * pct/100.0)`), `EpayRepository.ComputeFeeOrCommission` percent and per_thousand branches (`(double)` casts, `Math.Ceiling(double)`).
- **Consequence:** occasional 1-piaster differences between screen, receipt and report; non-deterministic on edge values.
- **Proposed fix:** integer math: `(bill * bps + 5000) / 10000`; `thousands = (bill + 99999) / 100000`; store fee percent settings as basis points.

### F-22 - Different "available drawer cash" checks give contradictory answers (consequence of F-02)
- **Category:** Cash control / UX. **Severity:** P2. **Confidence:** High.
- **Evidence:**
  - Shift cash-out (`CashDrawerService.cs` 150-160) checks against `ShiftRepository.CalculateShiftMetrics` (includes opening float, ignores e-pay/wallets/purchases).
  - Expenses (`ExpenseService.cs` 61-70), terminal funding (`EpayRepository.cs` 389), wallet funding (`DigitalAccountRepository.cs` 458), e-pay cash-out use `DailyClosingService.GetLiveDrawerBalance` (ignores opening float and manual cash-in/out).
- **Consequence:** at the start of the day the drawer physically holds the opening float, but expenses and fundings are refused ("insufficient cash") until sales arrive; after e-pay cash income, the shift cash-out check underestimates available cash, and vice versa.
- **Proposed fix:** resolved by the single calculator in F-02.

### F-23 - Expenses can be edited in place
- **Category:** Data integrity (violates AGENTS rule 2 "correction by contra entry"). **Severity:** P3. **Confidence:** High.
- **Evidence:** `ExpenseRepository.UpdateExpense` (~274+) updates amount/category/source of an existing expense row; only an audit log keeps the old value.
- **Consequence:** reports and any already-printed shift summaries diverge from stored data; history of the original amount depends on parsing audit JSON.
- **Proposed fix:** replace update with "cancel + recreate" (both rows kept, linked by `replaces_expense_id`), or keep an `expense_revisions` table.

### F-24 - Manual drawer cash-in / cash-out are not part of daily closing and have no closed-day check
- **Category:** Reconciliation. **Severity:** P2. **Confidence:** High. **Related:** F-02.
- **Evidence:** `CashDrawerService.RecordCashIn/RecordCashOut` (29-220) check only for an open shift; `DailyClosingService.GetClosingPreview` never reads `cash_drawer_transactions`.
- **Consequence:** owner taking 2,000 EGP from the drawer mid-day (cash_out) makes the daily closing show a 2,000 EGP shortage; owner adding change (cash_in) shows an overage.
- **Proposed fix:** include in unified calculator; block movements on a sealed business day.

## C4 findings (customer and supplier ledgers)

### F-25 - Debt payments rewrite `sales.paid_piasters` of old invoices, double-counting cash and changing historical reports
- **Category:** Financial / data integrity. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Process / roles:** customer debt settlement ("سداد الشكك"), daily closing, sales reports; cashier, owner.
- **Evidence:**
  - `desktop/Repositories/CustomerRepository.cs` 227-435 `RecordPayment`: FIFO allocation runs `UPDATE sales SET paid_piasters = paid_piasters + @alloc` on each unpaid invoice and inserts `payments` rows with method `debt_settlement`, then also writes a `customer_ledger` `payment` row.
  - `DailyClosingService.cs` 141-190 and `ShiftRepository.cs` 307-330: cash sales for `payment_method = 'credit'` = `MIN(paid - fee, total)`, for `cash` = `paid - fee - change`; credit sales = `total - (paid - fee)`. These are computed from the **current** `paid_piasters`.
  - Debt payments are added again via `customer_ledger` type `payment` (`DailyClosingService.cs` ~280).
- **Expected:** a sale row is immutable after commit; collections are separate events dated when they happen.
- **Actual:**
  - Same business day: credit sale 100, customer pays 100 later that day -> closing counts +100 as "cash sales" (paid_piasters grew) **and** +100 as "debt payments" -> expected cash is 100 too high -> false shortage blamed on cashier.
  - Past days: the reports for the original day change after the fact (credit sales shrink, cash sales grow), so a re-printed historical report no longer matches the sealed Z-report or the drawer count of that day.
- **Consequence:** wrong expected drawer cash every day credit is collected; historical sales/credit reports drift; customer analytics and aging see "paid" invoices that were paid on a different day.
- **Root cause:** using the sale row as both the invoice and a running "paid so far" balance.
- **Proposed fix:** never update `sales.paid_piasters` after creation; record allocations in a separate `debt_allocations(ledger_id, sale_id, amount)` table; derive "invoice outstanding" from it; closing uses `paid_piasters` (immutable, at-sale payment) + ledger payments by date.
- **Regression risk:** `ReturnService` credit-refund logic and debt aging use `paid_piasters`; must switch to the allocation table.
- **Tests:** credit sale 100 at 10:00, payment 100 at 15:00 same day -> closing cash +100 once; next-day payment -> yesterday's report unchanged.
- **Decision needed:** No.

### F-26 - Cancelling a customer payment hard-deletes `payments` rows and uses the calendar day for the closed-day check
- **Category:** Data integrity (violates AGENTS rule 2). **Severity:** P2. **Confidence:** High.
- **Evidence:** `CustomerRepository.cs` 535-570: `DELETE FROM payments WHERE id = @pid`; `UPDATE sales SET paid_piasters = MAX(0, paid_piasters - @amt)`; closed-day check `date('now','localtime')` (line ~512) ignores `business_day_cutoff_hour` (the payment path at line ~270 does use it - inconsistent). Reason defaults to "سجلت بالخطأ" when empty.
- **Consequence:** audit trail of allocations lost; after-midnight shops can cancel into a sealed day; `MAX(0, …)` hides mismatches.
- **Proposed fix:** with F-25's allocation table, insert reversing allocation rows; shared business-day helper (F-17); reason mandatory.

### F-27 - Credit limit and opening balance can be changed by anyone with `customers.create`
- **Category:** Authorization. **Severity:** P2. **Confidence:** High.
- **Evidence:** `IpcDispatcher.cs:293` maps `customers:save` -> `customers.create`; `CustomerRepository.SaveCustomer` (130-215) updates `credit_limit_piasters` for existing customers and inserts an `opening_balance` ledger entry for new ones from client values; no audit log for limit changes.
- **Consequence:** a cashier allowed to add customers can raise a friend's credit limit (removing the credit-limit block in `CreateSaleAtomic`) or create a customer with a negative "opening balance" (store owes the customer) and then take cash via a refund/withdrawal flow.
- **Proposed fix:** separate permissions `customers.credit_limit` and `customers.opening_balance`; audit old/new limit; opening balance only via a dedicated, audited command.

### F-28 - Returns to customer account do not reduce the invoice's outstanding amount
- **Category:** Business rule. **Severity:** P3. **Confidence:** Medium.
- **Evidence:** `ReturnRepository.cs` 557-613 decreases `customers.balance_piasters` and writes a `refund` ledger row but does not touch the FIFO-tracked outstanding of the original sale (`sales.paid_piasters`).
- **Consequence:** the returned invoice still appears "unpaid" in FIFO allocation; the next cash payment is allocated to goods the customer already returned; per-invoice aging and statements are misleading.
- **Proposed fix:** covered by F-25 allocation table (refund creates an allocation against the original invoice).

## C5 findings (inventory, purchasing, costing)

### F-29 - Saving a product overwrites stock with the value from the edit form (lost update)
- **Category:** Inventory integrity. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Process / roles:** product edit (price change, name change) while the POS keeps selling; owner, inventory manager.
- **Evidence:**
  - `desktop/Repositories/ProductRepository.cs` 638-700 `Upsert`: `ON CONFLICT DO UPDATE SET stock_quantity_milli = excluded.stock_quantity_milli, cost_piasters = excluded.cost_piasters`.
  - `desktop/Services/ProductService.cs` 200-300: no lock (`FinancialWriteLock` not taken), stock movement for the difference written afterwards in a **separate** `try { } catch { }`, outside the product transaction.
- **Scenario:** manager opens product (stock 50) to change the price; meanwhile POS sells 5 (stock 45); manager saves -> stock back to 50; the "adjustment" movement (+5 vs 45) is either recorded without reason or silently skipped if the catch fires.
- **Expected:** product edit never changes stock; stock changes only through sales, purchases, returns and audited adjustments (`inventory:adjustStock`, which requires a reason).
- **Consequence:** phantom stock, wrong reorder alerts, stock-movement ledger no longer sums to stock (`inventory:getDiscrepancies`), unexplained shrinkage at physical count.
- **Proposed fix:** remove `stock_quantity_milli` (and `cost_piasters` unless `products.edit_cost`) from the update branch of `Upsert`; initial stock only on insert, written in the same transaction as its `INITIAL` movement.
- **Tests:** concurrent sale + product save -> stock = original - sold.

### F-30 - Purchase invoices do not update the cost of non-base units (carton cost stays stale)
- **Category:** Costing / profit. **Severity:** P2. **Confidence:** High.
- **Evidence:** `PurchaseRepository.cs` 407-421 updates only `product_units WHERE is_base_unit = 1`. `SaleService.cs` 380-390 prefers `matchedUnit.CostPricePiasters` when > 0 for unit sales.
- **Consequence:** after a price increase from the supplier, cartons are still sold with the old carton cost -> profit on every carton sale overstated until someone edits the unit manually.
- **Proposed fix:** either recompute non-base unit cost = base cost x factor on every cost change, or stop storing unit cost and always derive it.

### F-31 - Two different purchase receiving paths with different side effects
- **Category:** Process / data integrity. **Severity:** P2. **Confidence:** High.
- **Evidence:** `inventory:recordPurchase` -> `InventoryService.RecordPurchase` (266-445): adds stock and optionally cost, but creates **no** `purchases` record, **no** supplier balance entry, **no** drawer cash movement, **no** batch, overrides cost without weighted average, uses `double` quantity (`Math.Round(purchaseQuantity * factor * 1000)`), audit log outside the transaction. `purchases:create` -> `PurchaseRepository.CreatePurchase` does all of these properly.
- **Consequence:** goods received through the quick path never appear in purchase reports or supplier statements; if paid from the drawer, the cash leaves without a record (false shortage).
- **Proposed fix:** remove or route `inventory:recordPurchase` through `CreatePurchase` (single path); keep multi-unit entry on the purchase screen.

### F-32 - Purchase returns are not validated against the original purchase and use client cost
- **Category:** Financial / fraud. **Severity:** P2. **Confidence:** High.
- **Evidence:** `PurchaseRepository.CreatePurchaseReturn` (679-950): `PurchaseId` optional and never checked; quantity not compared to purchased minus previously returned; `UnitCostPiasters` taken from the client; supplier balance reduced by `qty x client cost`; batch deduction uses `MAX(0, …)`; product cost (weighted average) not adjusted.
- **Consequence:** returning goods at an inflated cost reduces what the shop owes (or creates a fake supplier credit); returning more than was bought from that supplier is possible; batch and product stock can diverge.
- **Proposed fix:** require link to purchase line; cap quantity; take cost from the purchase line (`effectiveUnitCost`); keep batch and product deduction consistent.

### F-33 - Closed-day check for purchases paid from the drawer ignores the business-day cutoff
- **Category:** Reconciliation. **Severity:** P3. **Confidence:** High. **Related:** F-17, F-26.
- **Evidence:** `PurchaseRepository.cs` 157 `date('now','localtime')`; drawer check at 165 uses `DateTime.Now.ToString("yyyy-MM-dd")` instead of the business date.
- **Proposed fix:** shared business-day helper.

### F-34 - Purchases are recorded in base units only; carton conversion happens in the browser
- **Category:** Data integrity / UX. **Severity:** P3. **Confidence:** Medium. **Status:** Potential issue.
- **Evidence:** `PurchaseItem` has no `UnitId`/`ConversionFactor` (`grep ConversionFactor` in purchase code returns nothing); `frontend/src/views/purchases/NewPurchaseTab.tsx` 180-310 converts cartons/loose pieces client-side.
- **Consequence:** carton cost divided into piece cost in the browser may lose piasters (e.g. 100 EGP / 12); the original supplier document (cartons x carton price) cannot be reproduced from stored data, so supplier statement disputes are harder.
- **Proposed fix:** store unit, factor and package cost on the purchase line; compute base cost on the server with explicit remainder handling.

## C8 findings (security and authorization) - listed first because of severity

### F-35 - Hardcoded developer root account on every installation (backdoor)
- **Category:** Security vulnerability. **Severity:** P0 Critical. **Confidence:** High. **Status:** Static finding.
- **Evidence:** `desktop/Services/SecurityService.cs` 71-110 `NormalizeAdminRoles` (runs in the constructor at every start): creates user `islam` / id `usr_root_developer`, role `root`, password and PIN `8963906`, `MaxDepth 99`. If the user exists it is **re-activated** and its role forced back to `root` on every launch. The same PIN also appears as a hardcoded override in `SaleRepository.cs` 655 (F-06).
- **Expected:** no shared credential across customers; owner controls every account in their store.
- **Actual:** anyone who knows (or reads from the binary / this repository) `islam / 8963906` can log in to any customer's shop as root, approve any supervisor action (`VerifySupervisorPin` accepts root PINs), change users and permissions, export data, restore backups, factory-reset. The owner cannot disable it (it is re-enabled at next start).
- **Business consequence:** total loss of trust and possible legal exposure; insider fraud by any ex-employee who learns the code; data protection risk.
- **Proposed fix:** remove the auto-created account; for support, use a per-installation, time-limited support code (the license module already has `license:generateSupportCode`); migration that deactivates `usr_root_developer` on existing installs and logs it; rotate any other hardcoded secrets (F-06, F-37).
- **Tests:** fresh install has no `islam` user; existing install after upgrade: `islam` inactive and cannot log in or approve.
- **Decision needed:** D-7 (how vendor support access should work).

### F-36 - Supervisor PIN can be brute-forced without authentication or lockout
- **Category:** Security vulnerability. **Severity:** P1. **Confidence:** High.
- **Evidence:**
  - `auth:verifySupervisor` and `security:verifyPin` are **not** in `ACTION_PERMISSIONS` (`IpcDispatcher.cs` 190-483), so `AuthorizeRequest` returns `null` (allowed) - callable without login.
  - `SecurityService.VerifySupervisorPin` (965-1050) checks the lockout timer but **never increments** the failed-attempt counter on a wrong PIN, so the lockout never triggers through this path.
  - Includes accounts regardless of `IsActive` (`_userRepo.GetAll(true)`), and a plain-text comparison fallback for unsalted PINs ("1234" legacy).
- **Consequence:** a 4-digit supervisor PIN can be found in at most 10,000 calls (seconds), then used for discounts, credit-limit override, cancellations, expired-goods sale, returns without invoice. Deactivated (fired) managers' PINs keep working.
- **Proposed fix:** require a logged-in session for both actions; count failures per user and globally with exponential lockout; skip inactive users; remove plain-text fallback (force re-hash on upgrade).
- **Tests:** 5 wrong PINs -> locked; inactive admin PIN -> rejected; call before login -> `AUTH_REQUIRED`.

### F-37 - Default owner credential `admin / 1234`
- **Category:** Security. **Severity:** P2. **Confidence:** Medium (forced change on first login not yet verified).
- **Evidence:** `SecurityService.cs` 112-130 seeds `admin` with PIN `1234`.
- **Proposed fix:** first-run wizard must require setting the owner PIN; refuse `1234`/sequential PINs; verify in C10 whether this already exists.

### F-38 - Permission map is fail-open; several mutating actions have no permission entry
- **Category:** Authorization. **Severity:** P2. **Confidence:** High.
- **Evidence:** `IpcDispatcher.AuthorizeRequest` (~534): actions missing from `ACTION_PERMISSIONS` are allowed without login. Unmapped actions found: `products:runBulkPriceAdjustmentTests` (runs a test runner without admin check; it uses a temporary database, so the risk is CPU/disk abuse rather than data change - corrected in C11), `auth:verifySupervisor`, `security:verifyPin` (F-36), `auth:getActiveUsers` (user list before login), `auth:hasPermission`, `system:*`/`window:*`, `features:getAll`, `settings:getStoreProfile`, `health:getStatus`, `support:getSystemInfo`, `license:verify`, `license:checkExpiry`. Plus `templates:apply` explicit bypass (F-12).
- **Consequence:** any new action added without updating the map is open by default (AGENTS rule 8 depends on developer discipline only); test runners that mutate data reachable without admin.
- **Proposed fix:** default deny - unknown action -> `FORBIDDEN`; explicit `PUBLIC` allow-list for login/health/system UI actions; unit test that every `case "x:y"` string in `IpcDispatcher.*.cs` has a map entry.

## C7 findings (reports and data repair)

### F-39 - "Repair data quality" recalculates customer balances with an incomplete formula and overwrites them
- **Category:** Data integrity. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Evidence:** `desktop/Services/ReportsService.cs` 1950-1995 `RepairDataQualityIssues`: balance = `sale + opening_balance + debit_adjustment - payment - refund - credit_adjustment`; ignores `deposit`, `cancellation`, `payment_cancel`, `debt_increase`, `debt_decrease`; treats `opening_balance` as always positive (it is stored as absolute value, sign in `balance_after`). It then `UPDATE customers SET balance_piasters = calculated` for every mismatch. The canonical rule is `CustomerRepository.GetLedgerBalanceEffect` (638-660), which handles all types.
- **Scenario:** a customer with a cancelled credit invoice (ledger: sale +100, cancellation -100) -> repair computes 100 -> customer now owes 100 they do not owe. Customer with an advance (opening -50) becomes +50. Any customer with a cancelled payment loses that debt.
- **Consequence:** the button marketed as a safety tool silently corrupts customer debts for many customers at once, without per-customer audit entries.
- **Proposed fix:** reuse `GetLedgerBalanceEffect` (or the existing `customers:recalculateBalance` path) and log each correction with old/new value; show a preview before applying.
- **Tests:** customers with each ledger type -> repair makes no change when balances are already correct.

### F-40 - "Today" in dashboard and reports mixes UTC and local dates and ignores the business-day cutoff
- **Category:** Reporting. **Severity:** P2. **Confidence:** High.
- **Evidence:** `ReportsService.cs` 79, 111, 137 and `GetDateClause` default (~2048): `date(created_at,'localtime') = date('now','localtime') OR date(created_at) = date('now')`. All period filters use calendar `localtime` dates, not `business_day_cutoff_hour` used by sales, cancellation and daily closing.
- **Scenario (Egypt UTC+2/+3):** between 00:00 and 02:59 local, `date('now')` (UTC) is still yesterday, so the "OR" pulls all of yesterday's sales after 22:00/21:00 local into "today". After the cutoff hour logic, the dashboard "today" and the Z-report of the same business day disagree.
- **Consequence:** owner compares dashboard with Z-report and sees different numbers; cashier shift-change around midnight looks wrong.
- **Proposed fix:** one `BusinessDay` helper (same as F-17/F-26/F-33): `date(datetime(created_at,'localtime','-N hours'))` everywhere; remove the UTC `OR`.

### F-41 - Period reports repeat the closing defects and use inconsistent period lengths
- **Category:** Reporting. **Severity:** P3. **Confidence:** High.
- **Evidence:** `GetPeriodSalesReport` (680-860) and `GetTodaySummary` copy the closing SQL: overpayment counted as sales (F-03), cash/credit derived from mutable `paid_piasters` (F-25). `week` = `>= now - 7 days` (8 calendar days incl. today), `month` = 31 days, `year` = 366 days; no "this calendar month" option. `DashboardSummary.CashDrawerPiasters = TodayCashPiasters` (cash sales only, labelled as drawer cash).
- **Consequence:** "month" never matches the accountant's calendar month; "cash in drawer" on the dashboard ignores float, expenses, refunds, e-pay.
- **Proposed fix:** central report SQL fragments shared with closing; calendar periods (this week from Saturday, this month, last month); dashboard drawer value from the unified calculator (F-02).

## C9 findings (backup, restore, migrations, recovery)

### F-42 - Daily backups can only be decrypted on the same PC; a dead or reinstalled PC makes every backup useless
- **Category:** Data integrity / recovery. **Severity:** P1. **Confidence:** High. **Status:** Static finding.
- **Process / roles:** daily automatic backup, restore after hardware failure; owner, support.
- **Evidence:**
  - `desktop/Services/BackupService.cs` 299-303: every backup is encrypted with `EncryptionService` default constructor.
  - `desktop/Services/EncryptionService.cs` 30-110: key = PBKDF2(`MachineGuid | MachineName | ProcessorCount`, fixed app salt). No owner password, no exported recovery key.
  - `DatabaseService.RestoreFromBackup` (353-390) accepts an optional `masterKey`, but that only works if someone saved the *old PC's* fingerprint string beforehand (shown only via admin-only `security:getDeviceFingerprint`); nothing in the backup flow asks the owner to save it.
- **Expected:** the scenario backups exist for - hard disk failure, stolen/burned PC, Windows reinstall - must be recoverable on a new PC.
- **Actual:** new PC = new MachineGuid -> HMAC check fails -> "فشل التحقق من صحة التشفير". Even on the **same** PC, renaming the computer or replacing the CPU/changing core count (MachineName / ProcessorCount) breaks all existing backups. If the registry read fails, the key silently becomes a constant (`RAFIQ_DEFAULT_HARDWARE_GUID`), i.e. the same key on every such PC.
- **Business consequence:** total loss of sales history, customer debts ("دفتر الشكك") and supplier balances exactly when the shop needs the backup - the most damaging failure for a small Egyptian shop, where the debt book is the business.
- **Proposed fix:** encrypt backups with a random data key, wrap it with (a) the device key and (b) an owner recovery password/code printed once during setup ("كود استرجاع النسخ"); store the wrapped keys in the backup header; restore on a new PC asks for the recovery code. Add a "test restore on another PC" step to the onboarding checklist. Remove `MachineName` and `ProcessorCount` from key material.
- **Tests:** backup on PC A, restore on PC B with recovery code -> succeeds; without code -> clear Arabic message; rename PC A -> old backups still restore.
- **Decision needed:** D-8.

### F-43 - Main database and the "move to new PC" package are not encrypted, although the backlog marks database encryption as done
- **Category:** Security / privacy / documentation mismatch. **Severity:** P2. **Confidence:** High.
- **Evidence:** `DatabaseService.cs` 151 connection string has no password/encryption; backlog story 110 (#167 "تشفير قاعدة البيانات المحلية") is `[x]`. `MigrationService.CreateMigrationPackage` (246-370) zips `rafiq_pos.db` in plain form (`.rafiqpkg`).
- **Consequence:** anyone with file access (USB copy, technician) reads all customers' phones, debts, prices, costs and user list; the "move to new PC" file left on a USB stick is a full plain-text copy. The owner believes data is encrypted.
- **Proposed fix:** either implement encryption properly (SQLCipher-compatible build that still works on Windows 7) or correct the documentation and protect the migration package with the same recovery-code scheme as F-42.
- **Decision needed:** D-8.

### F-44 - Pre-migration safety copy can miss recent data and failures are ignored
- **Category:** Data integrity. **Severity:** P2. **Confidence:** High.
- **Evidence:** `MigrationRunner.cs` 1809-1833 `BackupDatabaseBeforeMigration`: `File.Copy(dbPath, …)` while the database is in WAL mode (pages in `rafiq_pos.db-wal` are not copied); `catch { }` swallows any failure and the migration continues; only the last 2 copies are kept. The restore path already uses the SQLite online backup API for exactly this reason (comment "Audit F-29" in `DatabaseService.cs` ~430).
- **Consequence:** if an upgrade migration damages data, the "safety" copy may lack the latest sales or not exist at all, and the owner is never told.
- **Proposed fix:** use `BackupDatabase` API (or checkpoint TRUNCATE first); abort the upgrade with a clear message if the safety copy fails; keep copies per version.

### F-45 - Client timeout on checkout can show "failed" for a sale that was saved
- **Category:** Reliability / UX. **Severity:** P3. **Confidence:** Medium. **Related:** F-09.
- **Evidence:** `frontend/src/bridge/ipc.ts` 266-310: default timeout 15 s for `sales:create`; on timeout the promise is rejected while the C# side may still commit. `PosView.tsx` ~985 shows "تعذر إتمام الفاتورة" and keeps the cart.
- **Consequence:** on slow Windows 7 machines (backup or antivirus running) the cashier sees failure, the customer leaves or pays again; if the cashier clears and re-rings, a duplicate invoice is created (the same cart key would be safe only while the app is not restarted, see F-09).
- **Proposed fix:** on timeout, query the sale by idempotency key before reporting failure; longer timeout for `sales:create`; persistent idempotency (F-09).

## C12 - Consolidated summary

### Product understanding
Rafiq is an offline Windows POS for small Egyptian supermarkets and service shops: retail sales (cash, card, InstaPay, wallets, credit "شكك", split), customer debt book, purchases and supplier balances, stock with units/batches/variants, e-pay bill-payment terminals and wallet cash-in/out services, shifts and a daily Z-report, backups and licensing. Architecture: React UI -> typed IPC -> C# services -> repositories -> SQLite (WAL), integer piasters.

### Overall assessment
- **Strong foundations:** integer money, atomic transactions under one lock, server-side recalculation of sale prices/costs, reversing entries for cancellations, return quantity/amount caps, authenticated backup encryption, consistent online backups, permission map on most actions.
- **Main weaknesses:**
  1. **Security trust boundary** - a built-in root account on every install (F-35), brute-forceable supervisor PIN (F-36), fail-open permissions (F-38), several client-trusted financial values (F-05, F-16, F-20).
  2. **Cash reconciliation** - no single definition of "expected drawer cash" (F-02, F-22, F-24) plus double counting of debt collections (F-25) and overpayments (F-03). The Z-report, which the owner uses to judge cashiers, cannot currently be trusted when credit, e-pay or wallets are used.
  3. **Business-day handling** - at least 7 different ways of deciding "which day is it" (F-17, F-26, F-33, F-40).
  4. **Mutable history** - sales rows, expenses, product stock and payment rows change after the fact (F-23, F-25, F-26, F-29), against the project's own rule 2.
  5. **Recoverability** - backups are bound to one PC (F-42).
  6. **Verification** - tests largely check copies or source text, so these defects were not caught (F-48-F-50).
